## 1. 재정리 축

| 대분류 | 키 | 성격 | 사용자가 하려는 것 |
|---|---|---|---|
| **분석** | `ANALYZE` | 조회·측정·비교 | 「지금 내 상태가 어떻지」 |
| **작성** | `WRITE` | 생성·검사·보조 | 「이 글을 만들어야지」 |
| **관리** | `MANAGE` | 추적·정리·관리 | 「올린 다음 계속 굴려야지」 |

데이터 출처(네이버·구글·유튜브)를 대분류에서 없앴다. 현행 「구글」 대분류는 항목이 하나뿐이라
반드시 재배치 대상이었고, 「네이버 데이터」는 사실상 *출처* 라벨이라 작업 흐름 축과 섞이지 않는다.

**소분류는 1단계까지만.** 현행처럼 대분류 > 소분류 > 기능 구조를 유지한다.

## 3. 판단이 갈린 기능 (확정하지 않음)

### 3-1. 키워드 추천 — 분석인가 작성인가
| 안 | 근거 |
|---|---|
| **작성 > 글** (제안) | 「무슨 글을 쓸까」의 답. 글감 찾기 바로 옆에 있어야 흐름이 이어진다 |
| 분석 > 키워드 | 나머지 키워드 기능 4개와 한 덩어리로 묶여 찾기 쉽다. 현행 위치이기도 하다 |

| 안 | 근거 |
|---|---|

## 4. §3 구조적 충돌 7건 — 처리안

### 4-0. 먼저: 3건은 조치가 필요 없다

### 4-1. §3.2 메뉴-라우트 계층 불일치 (3건)

|---|---|
| **㉮ 라우트 유지, 표시만 재분류 (권고)** | 링크·북마크·검색색인 전부 보존. §4.4 지시와도 일치 |
| ㉯ 라우트를 메뉴에 맞춰 이동 | 3개 URL 변경 + 리다이렉트 3개 신설. 얻는 것이 미관뿐 |

**권고 ㉮.** URL 계층이 메뉴 계층과 같아야 할 이유가 없다. 새 구조에서도 세 기능의 라우트는 그대로다.

### 4-2. §3.3 명칭 분산 (실제로는 최대 4종, 정의처 4곳)
| 선택지 | 결과 |
|---|---|
| **㉮ `label` 단일 정의처 신설 후 4곳이 읽기만 (권고)** | 재발이 구조적으로 불가능해진다 |
| ㉯ 이번만 4곳을 손으로 맞춤 | 다음에 또 갈라진다. 실제로 그렇게 갈라진 이력이 있다 |

**권고 ㉮.** 다만 정의처를 **새로 만들지 않는다** — 아래 §5 참조.

### 4-3. §3.6 이용권 항목 대응 (잔존 2건)
- 「MY 블로그」·「MY 키워드 챌린지」는 `SubscribeClient.tsx` 안에만 있는 문자열이다.
- **추측 매핑하지 않는다.** 오렌지 확인 전까지 §2 표에 `(?)` 로 남겨두었다.

### 4-4. §3.7 액션형 기능
- `kind: 'menu' | 'action'` 으로 구분한다(지시서 §6.1 그대로).
- 사이드바 배지로 표현할 수 없으므로 버튼 옆에 등급을 표기한다.
- 한도 분기 구현은 **불필요하다.** `csv.ts:46` 의 단일 상수 500 이 현재 판매 문구
  (양 등급 모두 「1회 500건」)와 일치한다 — 지시서가 전제한 「무제한」 표기는 이미 삭제됐다.

### 4-5. 명칭 통일로 함께 해소되는 것
「미노출 분석 → 노출 현황」, 「전체 리스트/인플루언서 랭킹/전체 인플루언서 → 인플루언서 순위」로
통일하면 §3.3 과 §3.5 가 한 번에 정리된다.

## 5. 구현 형태 제안 — `lib/features.ts` 를 새로 만들지 말 것

지시서 §6.1 은 `lib/features.ts` 신설을 지시하지만, **`src/lib/plans.ts` 가 이미
`FEATURES: Record<FeatureKey, FeatureDefinition>` 33개를 갖고 있다**(`key`·`label`·`minPlan`·
`allowAnonymous`·`consumesQuota`). 새 파일을 만들면 **정본이 둘로 갈라진다** — 이번 작업이
없애려는 바로 그 문제다.

| 선택지 | 결과 |
|---|---|
| **㉮ `plans.ts` 의 `FeatureDefinition` 을 확장 (권고)** | 필드만 추가: `category` · `subCategory` · `kind` · `route` · `apiRoutes` · `showInSidebar` · `order`. 기존 49개 API 가드가 그대로 동작한다 |
| ㉯ 지시서대로 `features.ts` 신설 후 `plans.ts` 는 등급만 | 개념은 깔끔하나 두 파일의 키를 영원히 동기화해야 하고, 이관 중 49곳이 깨질 위험 |

**권고 ㉮.** 「구조와 권한의 분리」는 파일을 쪼개지 않아도 같은 레코드 안의 필드 구분으로 달성된다.

### 함께 정리할 것
- `src/lib/dashboard-catalog.ts` 는 `PlanTier`(소문자) **한 줄만 남은 껍데기**인데 6개 파일이 참조한다.
  `PlanKey`(대문자)와 축이 겹치므로 통합 후 삭제 대상이다.
- `sidebar-nav.ts:3` 주석이 이미 사라진 `DASHBOARD_APPS` 를 가리킨다(stale).
