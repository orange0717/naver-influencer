# 서비스롤 → RLS 전환 계획 (초안, 미실행)

**상태: 계획 문서만 존재. 어떤 코드/DB 정책도 실제로 변경하지 않았음.**

## 배경

2026-08-02 전체 코드 리뷰에서 확인한 사실:

- API 라우트 251개 중 **206개(82%)** 가 `createServiceClient()`(service-role, RLS 완전 우회)를 사용
- `src/lib/supabase-server.ts`에 `createRouteHandlerClient()`(쿠키 세션 기반, RLS 적용됨)도 이미 존재하지만 거의 안 쓰임
- 마이그레이션 151개 중 54개가 이미 `ENABLE ROW LEVEL SECURITY` + 정책을 갖고 있음(예: `blog_scores`의 `public_read_blog_scores`) — 즉 DB 레벨 정책 자체는 일부 이미 있으나, 서비스롤 클라이언트를 쓰는 라우트에는 어차피 적용되지 않음
- 실질적으로 **권한 검증이 전부 애플리케이션 코드**(`getAuthUser`, `requireAdmin`, 수동 `.eq('user_id', ...)` 필터)에 의존 — DB는 안전망 역할을 하지 못함

## 왜 지금 자동으로 실행하지 않았는가

이건 "정리(cleanup)"가 아니라 **인증 모델 자체를 바꾸는 보안 아키텍처 변경**입니다. 잘못하면:
- RLS 정책을 잘못 설정하면 다른 유저의 데이터가 노출됨 (실제 침해 사고로 이어질 수 있음)
- 반대로 정책이 너무 엄격하면 서비스 자체가 조용히 인증 실패 상태가 됨 (기존 애플리케이션 레벨 필터와 이중 검증이 어긋나는 지점에서 발생)
- 251개 라우트 각각의 실제 접근 패턴(관리자 전용/본인 데이터/공개 읽기/크론 전용)을 개별적으로 분류해야 안전하게 정책을 쓸 수 있음
- 이번 세션 내내 Supabase 연결이 막혀 있어 **라이브 DB로 정책을 테스트할 방법이 없었음**

이런 변경은 되돌리기 어렵고(잘못된 정책이 이미 배포된 뒤 발견되면 데이터 노출이 이미 일어난 뒤), 자동화된 일괄 처리보다 테이블별 개별 설계 + 스테이징 검증이 필요합니다.

## 권장 단계

### 1단계 — 분류 (실행 전 필수)
251개 라우트를 접근 패턴별로 분류:
- **A. 관리자 전용** (`requireAdmin` 사용 중인 라우트, `admin/*` 대부분)
- **B. 본인 데이터만** (`my/*`, `profile/*` 등 — 이미 `.eq('user_id', authUser.userId)` 필터 존재)
- **C. 공개 읽기** (위젯, 랭킹 목록 등 — 이미 `public_read_*` 류 정책 존재하는 테이블)
- **D. 크론/시스템 전용** (`cron/*` — 실제로 서비스롤이 필요한 유일한 카테고리)

### 2단계 — 파일럿 (1개 테이블만)
가장 리스크가 낮은 카테고리(C. 공개 읽기, 예: `blog_scores`)부터 시작:
1. 이미 있는 `public_read_blog_scores` 정책이 실제로 필요한 컬럼만 노출하는지 재검토
2. 해당 테이블을 쓰는 라우트만 `createRouteHandlerClient()`(익명/세션 기반)로 전환
3. 스테이징 환경에서 정상 동작 + 비인가 접근 차단 둘 다 확인 후에만 다음 테이블로 진행

### 3단계 — 본인 데이터 카테고리 확산
B 카테고리(`my/*`)는 이미 애플리케이션 레벨에서 `user_id` 필터링이 되어 있으므로, RLS 정책은 "이중 안전장치"로 추가 — 정책: `auth.uid() = user_id` 형태. 각 테이블마다:
1. 정책 추가 (기존 서비스롤 코드는 그대로 두고 병행)
2. `createRouteHandlerClient()`로 전환한 사본 라우트를 별도 브랜치에서 테스트
3. 검증 후 전환, 문제 시 즉시 롤백 가능하도록 커밋 단위 분리

### 4단계 — 관리자 전용 (A)
`requireAdmin`은 그대로 유지(애플리케이션 레벨 관리자 판별은 계속 필요). RLS는 `is_admin` 클레임 기반 정책으로 보강.

### 유지할 것 (전환하지 않음)
- D 카테고리(크론)는 서비스롤이 정당한 용도 — 그대로 유지
- `requireAdmin`, `getAuthUser` 등 애플리케이션 레벨 인증 로직은 RLS 도입 후에도 제거하지 않음 (defense-in-depth)

## 다음 세션에서 시작할 때

1. 이 문서의 1단계(라우트 분류)부터 — 코드 변경 없이 목록만 작성
2. Supabase 연결이 복구된 상태에서, 스테이징 프로젝트(프로덕션과 분리된 별도 Supabase 프로젝트)에서 2단계 파일럿 진행
3. 절대 프로덕션에 직접 정책을 적용하며 테스트하지 않음
